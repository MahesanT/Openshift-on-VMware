01 / Architecture

Compact cluster. Real platform components.

The lab uses three schedulable RHCOS control-plane nodes on VMware vSphere. BIND9 provides the required cluster DNS records, vSphere CSI provides dynamic storage integration, and OpenShift ingress exposes applications through Routes.

02 / Build journey

From prerequisites to a healthy cluster.

The deployment was built using OpenShift installer-provisioned infrastructure (IPI) rather than manually creating RHCOS virtual machines.

1

Prepare vSphere and the installer host

Validated compute, datastore, network access and vCenter trust. The vCenter VMCA root certificate was imported into Ubuntu after the installer initially failed TLS verification.

2

Build authoritative lab DNS

BIND9 was configured for the API, internal API and wildcard application records, with forwarding for external Red Hat registry and RHCOS lookups.

dig @192.0.2.53 api.ocp.lab.example +short
dig @192.0.2.53 api-int.ocp.lab.example +short
dig @192.0.2.53 sample.apps.ocp.lab.example +short
3

Configure a compact IPI topology

Three control-plane replicas, zero dedicated workers, static networking and thin virtual disks were defined. A schema-placement issue with the OS disk field was corrected before deployment.

4

Run automated provisioning

The installer imported RHCOS, created bootstrap and master VMs, initialized the control plane, removed bootstrap and waited for cluster operators to stabilize.

Design lesson

Capacity matters before automation

The first provisioning attempt used thick virtual disks and reduced the selected datastore from 563 GB free to roughly 2.83 GB. The partial install was destroyed and rebuilt with thin disks.

04 / Troubleshooting

The failures were the useful part.

The project records what broke, how it was diagnosed and what changed. These are the scenarios that turned the lab into a platform-engineering exercise rather than a simple install walkthrough.

vCenter certificate trust

Symptom: x509 unknown authority.
Fix: imported the verified vCenter VMCA root into the Ubuntu trust store instead of disabling installer verification.

External DNS failure

Symptom: RHCOS mirror resolution failed while internal records worked.
Fix: configured BIND9 forwarders and corrected systemd-resolved DNS routing.

Datastore nearly full

Symptom: free capacity collapsed during provisioning.
Fix: stopped the partial deployment, used installer destroy state, and redeployed with thin disks.

NGINX CrashLoopBackOff

Symptom: permission denied creating NGINX cache paths under OpenShift SCC.
Fix: moved to the unprivileged NGINX image rather than weakening SCC security.

Deployment image reverted

Symptom: a manual image change was overwritten.
Fix: discovered an ImageStream trigger selecting the old image, removed the trigger and updated the Deployment.

Service reached the wrong port

Symptom: the unprivileged image listened on 8080 while the Service targeted 80.
Fix: corrected targetPort and replaced the ReplicaSet hash selector with a stable Deployment-level selector.

05 / Application validation

Pod → Service → Route → client.

The final NGINX workload used an image compatible with OpenShift's restricted non-root security model and was exposed through an OpenShift Route.

Workload correction

Use a non-root compatible image

oc annotate deployment/demo-pod image.openshift.io/triggers- -n demo

oc set image deployment/demo-pod   nginx=nginxinc/nginx-unprivileged:stable -n demo

oc rollout status deployment/demo-pod -n demo
Network validation

Expose and test the Route

oc expose svc/nginx-svc --name=nginx-route -n demo
oc get svc,route -n demo
oc get endpoints nginx-svc -n demo

curl -I http://<route-host>
# HTTP/1.1 200 OK
✓ Verified result: the deployed application returned HTTP/1.1 200 OK with nginx/1.30.6, validating the application path through OpenShift ingress.
06 / Microservices application

Sock Shop on OpenShift.

As a second application exercise, I deployed the Sock Shop microservices demo into the sock-shop namespace. All 13 Deployments were confirmed running after adapting several legacy services to OpenShift's restricted security model.

🧦
Application

13 microservices

carts, catalogue, orders, payment, shipping, user, front-end, RabbitMQ and their supporting database services.

🔒
Security

Restricted execution

Legacy services expecting privileged ports or executable capabilities had to be adapted rather than bypassing OpenShift SCC protections.

↗
Exposure

Front-end Route

The Sock Shop front-end Service can be exposed through an OpenShift Route after validating Pods, Services and endpoints.

Java services

Move application listeners to 8080

for app in carts orders queue-master shipping; do
  oc set env deployment/$app SERVER_PORT=8080 -n sock-shop
done

oc get deployments -n sock-shop
oc get pods -n sock-shop
Front-end access

Expose the microservices UI

oc expose service/front-end -n sock-shop
oc get route front-end -n sock-shop
oc get svc,endpoints -n sock-shop
✓ Verified result: all 13 Sock Shop deployments were confirmed running after the OpenShift compatibility fixes. A complete browse/cart/checkout transaction was not recorded, so the portfolio does not claim full transactional validation.
